# DSH 插件生态与 dsh-voice 竞争分析

日期：2026-11-06

## 生态信号

DeepSeek 官方披露：DSH 日活约 154 万，日消耗约 92 万亿 Token，第三方插件约 3.5 万个，约 60% 的活跃用户制作或安装过至少一个第三方插件。插件已经不是附属功能，而是 DSH 的主要使用界面。

官方点名的四个插件：

| 插件 | 作者 | 本质 | 可借鉴的点 |
|---|---|---|---|
| `dsh-media-desk` | woniuniuniu | 自媒体工作台：灵感、内容、排期、复盘、风格五个页面 | 有自己的数据、工作流和日历，不是单个按钮 |
| `dsh-guizang-design` | op7418 | 设计工作台：五个 skill、设计系统、作品库、语气档案、内容工作流 | Skill + 插件页面 + 持久化作品库 |
| `dsh-context` | bowenliang123 | 上下文可观测性：统计、组成、趋势、浏览器、Agent 网络 | 读取宿主真实数据，做诊断和决策 |
| `agentero-dsh` | Phil-Fan | 本地科研工作台：文献库、PDF 阅读、批注、翻译、笔记 | 把外部专业工具接进 DSH，数据留在本地 |

四个插件共同点：

1. **有自己的工作台**，不是只加一个输入按钮。
2. **有持久数据**：作品、排期、文献、笔记、上下文历史。
3. **模型负责生成，插件负责结构、存储和流程**。
4. **都解决一个反复发生的专业工作流**，不是泛化的“AI 功能”。
5. **README 有真实截图、安装路径、限制和隐私说明**，用户能判断是否可信。

## Voice 类插件现状

`awesome-dsh-plugin` 目录里 `voice` 分类约有 112 个条目。大多数集中在三件事：

- TTS 朗读：接 Edge、豆包、GPT-SoVITS、Kokoro 等，做一个朗读按钮或自动朗读。
- 听写输入：麦克风转文字进输入框，部分带热词、麦克风选择、润色。
- 提示音/通知：任务完成、授权请求、错误时播放声音。

代表性项目：

| 项目 | Star | 做什么 | 对我们的意义 |
|---|---:|---|---|
| `dsh-tts-bridge` | 217 | 借 DeepSeek 网页端朗读，浏览器扩展配合 | 说明“朗读”是最大众的需求，但方案很薄 |
| `dsh-omi-voice` | 75 | 豆包自然音色朗读，点读/暂停/继续，BYOK | 音色和朗读体验可以单独成立 |
| `dsh-plugin-tts` | 51 | Edge TTS / RVC 朗读 | TTS 供给已经过剩 |
| `dsh-voice-mode` | 28 | 流式识别、按句朗读、打断、唤醒词、按住说话、字幕、18 个宿主版本验证 | 最直接的全双工竞品，功能面比我们宽 |
| `dsh-voice-scribe` | 36 | 听写优先，SenseVoice、本地/浏览器/云端回退、热词、设备选择 | 听写体验比我们完整 |
| `dsh-duet` | 13 | 云端全双工语音模型、语音控制会话、3D 形象 | 已经在做“语音操作 DSH”，但依赖服务器 |

结论：**语音输入和朗读已经是红海。** 继续加音色、加 ASR 模型，只会进入同质化竞争。真正稀缺的是“语音作为 DSH 的控制层”和“可验证的全双工可靠性”。

## 我们的位置

已有优势：

- 真全双工处理结构：播放期持续识别、开口打断、3 秒回灌。
- 语音审批：DSH `approval/request` 直接说允许/拒绝，这是目前很少见的深度集成。
- 本地 ASR + 本地/云端 TTS 可切换；火山、阿里百炼、MiniMax 三家云端 TTS。
- 模型首次使用自动下载，默认魔搭，SHA256 校验。
- 界面干净，光球和字幕已经达到可展示水平。
- DSH 0.1.5 / 0.2.1 / 0.2.2 实测，Release 可安装。

明显短板：

- 功能面落后 `dsh-voice-mode`：没有唤醒词、按住说话、朗读范围、字幕档位、热词、设备选择、会话控制。
- 没有 npm 包和插件市场条目，分发弱。
- 没有真实外放 AEC 和跨平台设备矩阵，不能声称“所有设备都能稳定打断”。
- 没有和任何垂直工作台打通，仍是“一个通用语音按钮”。
- 没有英文 UI，海外用户门槛高。

## 机会判断

有机会，但不是把 TTS 做得更多。我的判断：**把 dsh-voice 从“语音输入插件”改成“DSH Agent 的语音控制层”。**

### 机会一：Agent 语音控制台（最高优先）

DSH 的 Agent 会长时间运行、请求授权、产生 diff、消耗上下文。用户离开键盘时，现在只能看屏幕。语音可以承担：

- “现在在做什么 / 还剩多少上下文 / 读一下最后一条”
- “批准 / 拒绝 / 停止 / 继续 / 重试”
- “切到第二个会话 / 新建一个会话”
- “读一下这个 diff / 总结这一轮”
- “把这个任务记下来”

我们已经有语音审批，把它扩展成**受控 intent 路由**，而不是自由文本命令。破坏性操作必须二次确认，只允许白名单动作。这是 `dsh-duet` 已经在做但依赖云端的方向；我们的本地优先和审批桥可以做得更稳。

### 机会二：给其他插件提供 Voice Intent API

官方点名的四个插件都是工作台。它们都需要“说话”这个入口，但不应该各自造一套 ASR/TTS/打断。

我们可以提供：

- 插件注册语音 intent，例如 `media-desk.create-from-idea`、`guizang.change-theme`、`context.explain-usage`。
- dsh-voice 统一处理麦克风、VAD、ASR、TTS、打断、确认。
- 其他插件只声明“用户这样说时调用我”，不碰音频。

这会让我们从“112 个 voice 插件之一”变成“voice 插件的基础设施”。DSH 有 3.5 万个插件，这个位置比再做一个朗读按钮大得多。

### 机会三：把可靠性做成证据

竞品 README 已经在讲 18 个宿主版本、15 个隔离核心冒烟。我们目前只有“macOS 已实测”。

需要补：

- 真实外放 AEC 测试：耳机 / 外放 / 不同音量 / 噪声。
- 误打断率、打断停止延迟、首声延迟的 p50 / p90。
- 设备矩阵：macOS / Windows / Linux，至少各一台真实设备。
- 公开测试音频和复现脚本。

这类证据不影响功能数量，但决定用户是否敢在会议、开车、厨房这种真实场景使用。

### 机会四：移动端和英文市场

`dsh-media-desk` 已明确支持手机浏览器。语音是移动端最自然的输入方式。当前 UI 没有移动布局，也没有英文界面；这两项会直接限制用户盘子。

## 建议路线

### 0–2 周

- 发布 npm 包，进入 `awesome-dsh-plugin`（仓库满 1 天后）。
- 英文 UI 和英文 README 首屏。
- 补一页真实的延迟/打断测试数据，不再只说“已实测”。
- 把 `dsh-voice-mode` 的功能差距列成表，只补与“控制层”相关的项。

### 2–4 周

- 做 Agent 语音控制：状态、上下文、停止、继续、重试、切换会话。
- 审批从“允许/拒绝”扩展为“允许一次 / 总是允许 / 拒绝 / 先看 diff”。
- 所有破坏性 intent 加确认和审计日志。

### 4–8 周

- 定义 Voice Intent API，先接一个官方点名的工作台做试点。
- 优先 `dsh-context`：语音问“现在上下文为什么涨了”，这是天然契合。
- 或 `dsh-media-desk`：语音记灵感、语音改稿，直接展示“语音工作台”价值。

### 不建议做

- 不要继续堆 TTS 音色；TTS 已经商品化。
- 不要为了对齐 `dsh-voice-mode` 把所有功能都做一遍；那会变成功能竞赛。
- 不要在没有 AEC 证据时宣传“任何设备都能打断”。
- 不要从零做一个垂直工作台；我们没有那个领域的内容资产，合作/语音赋能更快。

## 一句话

**别人做的是“在 DSH 里多一个工作台”；我们应该做“让所有工作台都能被语音操作”。** 语音审批是切入点，Voice Intent API 是护城河。

## 配音工作台机会（2026-11-06 追加）

先说结论：**可以做，但不要做“什么都配”的通用配音工具。** 通用配音已经是红海，真正有空位的是“多角色、可导演、可复用”的 DSH 原生配音工作台。

### 外部市场

用户记得的项目很可能是：

- `debpalash/VoiceStudio`：102k★，AGPL-3.0，本地 ElevenLabs 替代，含声音克隆、声音设计、视频配音、听写、有声书，646 种语言，已有 Pro / Cloud 商业化
- `abus-aikorea/voice-pro`：13.4k★，Gradio WebUI，Edge/Kokoro TTS、零样本克隆、Whisper、YouTube 下载、Demucs、翻译
- `jianchang512/pyvideotrans`：19.6k★，视频翻译 + 配音 + 字幕
- `Huanshere/VideoLingo`：19.1k★，字幕切割、翻译、对齐、配音
- `buxuku/SmartSub`：6k★，字幕、翻译、AI 配音、声音克隆、烧录

这些项目证明需求真实，但也说明“能配音”本身不是壁垒。直接做一个同类产品，会同时打模型、桌面端、格式兼容和免费生态四场仗。

### DSH 内部市场

DSH 已经有相邻能力：

- `tongflow#dsh-tongflow` 1049★：图片、配音、音乐、视频的“片场”，按镜头/角色/take 组织项目
- `dsh-video-pipeline`：19 个 skill，含中文配音读音校正
- `podflow-studio` 87★：播客分段配音、音质检查、RSS
- `indextts2-longform-workbench` 55★：长篇台本、多轨时间轴、批量配音、工程导出
- `dsh-audiobook`、`dsh-tingdong`、`any-audio`、`dsh-voice-remix`：朗读、有声书、音频工具

所以空位不是“没有配音工具”，而是：**没有一个以“角色 casting + 多 take + 导演式修改”为中心、又能和 DSH Agent 的工作流数据打通的配音工作台。**

### 建议的产品切口

不要按“人群”切，先按**内容形态**切：

1. **多角色剧情/短剧配音**：角色识别、音色 casting、情绪/语速、同角色跨集一致性、take 对比
2. **课程/企业培训**：术语读音、章节、版本、批量导出、多人协作
3. **有声书**：章节、角色、长文本、断句、章节级返工
4. **跨境电商/出海视频**：翻译 + 多语言配音 + 字幕 + 时长对齐

第一版只做一个：**多角色剧情/口播配音**。人群预设以后再加，不要一开始就做五个行业。

### MVP 范围

先做“台本 → 多角色音频”，不要一上来碰视频时间线：

- 粘贴/导入台本，自动识别 `角色：台词`
- 角色表 + 音色库 + 每个角色的默认语速/情绪
- 逐句生成、试听、重生成单个 take
- 发音词典（人名、术语、品牌名）
- 导出多轨 WAV/MP3 + SRT
- 项目持久化，可回到任意一句改

第二阶段再加视频导入、ASR/说话人分离、翻译、时间轴、ducking、MP4 导出。第三阶段再接声音克隆/声音设计，并加同意书和审计。

### 和 dsh-voice 的关系

`dsh-voice` 继续做通用语音运行时：ASR、TTS、打断、审批、Voice Intent API。配音工作台是一个垂直 pack，复用它的 TTS 适配器和模型管理，不把配音项目数据塞进语音插件。

### 商业判断

- 免费开源核心 + BYOK 云音色，卖工作流而不是卖 Token
- 付费点：团队协作、项目版本、批量任务、商用授权、声音库、托管渲染
- 最大风险不是技术，是 VoiceStudio / pyVideoTrans 这类免费工具的替代，以及声音克隆的授权合规
- 最稳的差异化：DSH 原生、Agent 可导演、项目数据留在本地、能和媒体/设计工作台串成流水线

一句话：**通用配音是红海；“多角色、可导演、DSH 原生”的配音工作台还有位置。**
